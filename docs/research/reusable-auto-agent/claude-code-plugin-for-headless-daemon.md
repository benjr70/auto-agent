## Short answer

**Mostly yes, with two hard exceptions.** A plugin can carry skills, subagent definitions, hooks (including `TaskCompleted`, `TeammateIdle`, `UserPromptSubmit`) and MCP server entries, and `claude --permission-mode bypassPermissions --print "/afk:afk-pickup" --plugin-dir /path/to/plugin` loads it non-interactively from any directory without installing anything into the Target Project checkout ([plugins-reference](https://code.claude.com/docs/en/plugins-reference), [cli-reference](https://code.claude.com/docs/en/cli-reference)). What a plugin **cannot** carry:

1. `settings.json` `env` and `permissions` blocks. A plugin's shipped `settings.json` honours only the `agent` and `subagentStatusLine` keys ([plugins](https://code.claude.com/docs/en/plugins#ship-default-settings-with-your-plugin)). Env and permissions must come from the Host (`~/.claude/settings.json`, `--settings`, or the process environment).
2. Agent Teams at all under `--print`: "Spawning teammates also requires an interactive session. In non-interactive mode with the `-p` flag ... Claude doesn't spawn teammates, and a subagent that Claude names runs as an ordinary subagent even with agent teams enabled" ([agent-teams](https://code.claude.com/docs/en/agent-teams)). This is independent of plugins: the Smart Smoker "roster" already runs as plain subagents under the Daemon, so `TeammateIdle` never fires there and `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` is inert for a Fire.

Two softer caveats: plugin subagents ignore the `hooks`, `mcpServers` and `permissionMode` frontmatter fields ([sub-agents](https://code.claude.com/docs/en/sub-agents#choose-the-subagent-scope)), and plugin skills are always namespaced (`/afk:afk-pickup`, never `/afk-pickup`) ([plugins](https://code.claude.com/docs/en/plugins#quickstart)).

## Sub-questions

### 1. Plugin manifest layout and supported component types

Layout ([plugins-reference, "Plugin directory structure"](https://code.claude.com/docs/en/plugins-reference#plugin-directory-structure)): manifest at `.claude-plugin/plugin.json` (optional if components use default locations; `name` is the only required field), and at the plugin root: `skills/<name>/SKILL.md`, `commands/*.md`, `agents/*.md`, `hooks/hooks.json`, `.mcp.json`, `.lsp.json`, `workflows/`, `output-styles/`, `monitors/monitors.json` (experimental), `themes/` (experimental), `bin/` (added to Bash `PATH` while enabled), `scripts/`, and `settings.json`. "Don't put `commands/`, `agents/`, `skills/`, or `hooks/` inside the `.claude-plugin/` directory" ([plugins](https://code.claude.com/docs/en/plugins#plugin-structure-overview)).

Manifest fields ([plugins-reference, manifest schema](https://code.claude.com/docs/en/plugins-reference#plugin-manifest-schema)): `name`, `version`, `description`, `author`, `homepage`, `repository`, `license`, `keywords`, `skills` (adds to the default scan), `commands`/`agents`/`workflows`/`outputStyles` (replace defaults), `hooks` (path or inline), `mcpServers` (path or inline), `lspServers`, `experimental.{themes,monitors}`, `userConfig`, `channels`, `dependencies` (with semver constraints), `defaultEnabled`. Paths are relative to the plugin root and start with `./`.

Component types relevant to the harness:

| Harness piece today (Smart Smoker) | Plugin carrier | Notes |
|---|---|---|
| `.claude/skills/afk-*/SKILL.md` | `skills/<name>/SKILL.md` | Namespaced `/plugin-name:skill-name`. Skills can also be run in a subagent and can preload into agents via `skills:` frontmatter ([skills](https://code.claude.com/docs/en/skills)). |
| `.claude/agents/{implementer,reviewer,verifier}.md` | `agents/*.md` | Lowest precedence (priority 5); project/user files with the same name override the plugin copy ([sub-agents](https://code.claude.com/docs/en/sub-agents#choose-the-subagent-scope)). Frontmatter `hooks`, `mcpServers`, `permissionMode` are ignored for plugin agents. Subfolders become part of the scoped id (`afk:review:security`). |
| `settings.json` `hooks` (`TaskCompleted`, `TeammateIdle`, `UserPromptSubmit`) | `hooks/hooks.json` | Same event list as user hooks, including all three ([plugins-reference, Hooks](https://code.claude.com/docs/en/plugins-reference#hooks)). "When a plugin is enabled, its hooks merge with your user and project hooks" ([hooks](https://code.claude.com/docs/en/hooks)). Scripts referenced as `${CLAUDE_PLUGIN_ROOT}/scripts/...`. |
| `.mcp.json` | `.mcp.json` at plugin root or inline `mcpServers` | "Plugin MCP servers work identically to user-configured servers"; started when the plugin is enabled; tool names are scoped `mcp__plugin_<plugin>_<server>__<tool>` ([mcp](https://code.claude.com/docs/en/mcp#plugin-provided-mcp-servers)). |
| `scripts/claude-agent/lib/*.sh` | `scripts/` (or `bin/` for PATH) | Referenced via `${CLAUDE_PLUGIN_ROOT}`; exported as an env var to hook processes and substituted in skill/agent text ([hooks](https://code.claude.com/docs/en/hooks#reference-scripts-by-path)). `${CLAUDE_PLUGIN_DATA}` (`~/.claude/plugins/data/<id>/`) survives updates for state/deps ([plugins-reference](https://code.claude.com/docs/en/plugins-reference#persistent-data-directory)). |
| `settings.json` `env`, `permissions` | **Not carried** | Only `agent` and `subagentStatusLine` keys; "Unknown keys are silently ignored" ([plugins](https://code.claude.com/docs/en/plugins#ship-default-settings-with-your-plugin)). |
| Per-Host secrets / repo name | `userConfig` | Prompted at enable time; in headless mode passed via `--settings '{"pluginConfigs":{"<id>":{"options":{...}}}}'` or managed settings; read from user settings only, not project `.claude/settings.json` since 2.1.207 ([plugins-reference, user configuration](https://code.claude.com/docs/en/plugins-reference#user-configuration); [CHANGELOG 2.1.207](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)). Exposed as `${user_config.KEY}` and `CLAUDE_PLUGIN_OPTION_<KEY>`. |

### 2. `--plugin-dir` / marketplace / `enabledPlugins`

- `--plugin-dir <path>`: "Load a plugin from a directory or `.zip` archive, or several from a folder of plugins, for this session only. Each flag takes one path. Repeat the flag for more paths" ([cli-reference](https://code.claude.com/docs/en/cli-reference)). Folder-of-plugins needs 2.1.265+ (CHANGELOG 2.1.265). A `--plugin-dir` plugin with the same name as an installed marketplace plugin wins for that session (CHANGELOG 2.1.74; [plugins](https://code.claude.com/docs/en/plugins#test-your-plugins-locally)). It is not persisted and is not listed by a bare `claude plugin list` ([plugins-reference](https://code.claude.com/docs/en/plugins-reference)). Its identity is `<name>@inline`.
- `--plugin-url <url>`: fetch a `.zip` for the session only; load failures are recorded and the session starts without the plugin (CHANGELOG 2.1.129; [plugins](https://code.claude.com/docs/en/plugins#test-your-plugins-locally)).
- Marketplace install: `claude plugin install <name>@<marketplace> --scope user|project|local`; `--yes` is required when stdin/stdout is not a TTY for `command`-sourced plugins or `headersHelper` archives ([plugins-reference, CLI commands](https://code.claude.com/docs/en/plugins-reference#plugin-install)). Marketplace sources: `github`, `url`, `git-subdir`, `npm`, `archive`, `command`, local `directory`/`file`, and inline `settings` ([plugin-marketplaces](https://code.claude.com/docs/en/plugin-marketplaces)). Installed copies live in `~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/`; marketplace state in `~/.claude/plugins/known_marketplaces.json` (once per user, not per project).
- `enabledPlugins`: object mapping `plugin-name@marketplace-name` to a boolean; any scope (user, project, local, managed, `--settings`) ([settings-reference](https://code.claude.com/docs/en/settings-reference#enabledplugins)). A project `.claude/settings.json` can carry `extraKnownMarketplaces` + `enabledPlugins` so collaborators get the marketplace added once they trust the folder ([plugin-marketplaces, "Require marketplaces for your team"](https://code.claude.com/docs/en/plugin-marketplaces#require-marketplaces-for-your-team)). But under `claude -p` in a never-trusted folder, `extraKnownMarketplaces` entries from the repository or an `--add-dir` directory are "Not used" ([permissions, "What runs before you trust a folder"](https://code.claude.com/docs/en/permissions#what-runs-before-you-trust-a-folder)), and a plugin enabled only by a project's settings needs explicit install consent (CHANGELOG 2.1.195, 2.1.207 fixes). So for a Daemon, the marketplace must be registered on the Host at user scope (or seeded, see §6).
- Headless config without prompts: `claude --settings '{"enabledPlugins": {"my-plugin@mkt": true}}'` and `pluginConfigs` via `--settings` ([plugins-reference](https://code.claude.com/docs/en/plugins-reference)).
- Skills-directory plugins: any folder under `~/.claude/skills/` (personal) or `<cwd>/.claude/skills/` (project) with a `.claude-plugin/plugin.json` loads as `<name>@skills-dir` with no install step. Personal scope has no restrictions; project scope requires the workspace trust dialog ("running with `-p` isn't enough") and loads only from the primary working directory ([plugins-reference, Skills-directory plugins](https://code.claude.com/docs/en/plugins-reference#skills-directory-plugins)). `claude plugin init <name>` scaffolds one at `~/.claude/skills/<name>/`.
- Managed settings can reject the sideload flags entirely via `disableSideloadFlags` (`--plugin-dir`, `--plugin-url`, `--agents`, `--mcp-config`) ([settings-reference](https://code.claude.com/docs/en/settings-reference#disablesideloadflags)); not relevant unless the Host is under an org policy.

### 3. Can project-scoped `.mcp.json` and hooks come from a plugin?

Yes for both, as an equivalent rather than a literal project file:

- Hooks: plugin `hooks/hooks.json` is one of the documented hook locations ("Scope: when plugin is enabled; Shareable: yes, bundled with the plugin") and runs inside subagents too ([hooks](https://code.claude.com/docs/en/hooks)). All matching hooks run in parallel; a plugin's copy of a handler that duplicates a settings-file handler "stays separate" (it would run twice), so move, don't copy, the hooks out of the Target Project's `settings.json`.
- MCP: plugin `.mcp.json` servers start automatically when the plugin is enabled and sit at precedence 4 (below local, project, user) ([mcp, scope hierarchy](https://code.claude.com/docs/en/mcp#scope-hierarchy-and-precedence)). Approval: the interactive per-server prompt applies to a *project* `.mcp.json`; in `claude -p` runs Claude Code "loads project-scoped servers without asking" ([mcp, project scope](https://code.claude.com/docs/en/mcp#project-scope)). The docs do not state any approval step for plugin-provided servers outside project-scope `@skills-dir` plugins, which "go through the same per-server approval as a project `.mcp.json`" ([plugins-reference](https://code.claude.com/docs/en/plugins-reference#skills-directory-plugins)). Approval prompting for `--plugin-dir` plugin servers under `-p`: not documented; the `-p` rule above (no prompt shown, servers load) is the operative one.
- `${CLAUDE_PROJECT_DIR}` is substituted directly in plugin MCP configs (no `:-.` default needed), so the current `bash -c 'git rev-parse --show-toplevel'` wrappers can become `${CLAUDE_PROJECT_DIR}` ([mcp](https://code.claude.com/docs/en/mcp)).
- The orphaned-MCP-server problem noted in the map (#1, §6.1) is not addressed by plugins: plugin servers "connect and disconnect" with the session, same lifecycle as any stdio server ([mcp, plugin MCP features](https://code.claude.com/docs/en/mcp#plugin-provided-mcp-servers)). Not documented: any reaping guarantee.

### 4. `--add-dir` and `CLAUDE_CONFIG_DIR`

- `--add-dir` grants file access and loads only a short list of configuration from the added directory: `.claude/skills/` (live reload), `.claude/commands/` and `.claude/agents/` (no reload), and from `.claude/settings.json` only the `enabledPlugins` and `extraKnownMarketplaces` keys; `CLAUDE.md` only with `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1`. Hooks, `env`, `permissions` and `.mcp.json` are **not** loaded from an added directory ([permissions, "Additional directories grant file access, not configuration"](https://code.claude.com/docs/en/permissions#additional-directories-grant-file-access-not-configuration)). Those items load through the `project` setting source, so `--setting-sources user` drops them. `permissions.additionalDirectories` in settings loads none of them.
- So `--add-dir <harness-checkout>` is a viable *partial* carrier (skills + agents) but not for hooks or MCP; a plugin is strictly more complete.
- `CLAUDE_CONFIG_DIR` "overrides the configuration directory (default `~/.claude`). All settings, session history, and plugins are stored under this path"; set it in the shell, user settings, or managed settings; it is ignored in project and local settings (`env` block) ([env-vars](https://code.claude.com/docs/en/env-vars); CHANGELOG 2.1.251). Pair with `CLAUDE_CODE_PROJECT_DIR_NAME` (2.1.234+) to choose the `projects/<name>/` transcript directory. Interaction with `--add-dir`: not documented beyond the above; they are orthogonal (one relocates the user config root, the other adds working directories). For a Host running several Daemons, one `CLAUDE_CONFIG_DIR` per Daemon gives each its own `settings.json`, login, plugin cache and transcripts (the Dashboard's transcript scraping would key on this path).

### 5. Agent Teams and teammate definitions from a plugin

- Teammate roles can reference "a subagent type from any subagent scope: project, user, plugin, or CLI-defined" ([agent-teams, "Use subagent definitions for teammates"](https://code.claude.com/docs/en/agent-teams#use-subagent-definitions-for-teammates)). Applied parts: `tools`, `model`, body; `skills` is ignored for teammates; `mcpServers` applies only to split-pane teammates.
- However, teammates do not exist under `--print` at all (quoted in the short answer; [agent-teams, "Enable agent teams"](https://code.claude.com/docs/en/agent-teams)). CHANGELOG 2.1.71 ("Fixed `--print` hanging forever when team agents are configured") is the historical marker. Consequences for the Daemon: the implementer/reviewer/verifier roster runs as ordinary subagents; `TeammateIdle` never fires; `TaskCompleted` still fires when a subagent calls `TaskUpdate` ([hooks, TaskCompleted](https://code.claude.com/docs/en/hooks#taskcompleted)), so the `smoke:` trailer gate keeps working only through that path.

### 6. Version pinning and upgrade

- Version resolution ([plugins-reference, "Version management"](https://code.claude.com/docs/en/plugins-reference#version-management)): `plugin.json` `version` > marketplace entry `version` > git commit SHA (for `github`/`url`/`git-subdir`/relative-path sources) > archive SHA-256 > `unknown`. Explicit version means "users get updates only when you bump this field"; omitting it yields commit-SHA versioning ("Internal or team plugins under active development").
- Marketplace entries pin with `ref` (branch/tag) and `sha` (40-char commit); when both are set, `sha` is the effective pin ([plugin-marketplaces](https://code.claude.com/docs/en/plugin-marketplaces)). Archive sources pin with `sha256`.
- Updates: `claude plugin update <plugin>` (restart required); background auto-update is on by default only for official Anthropic marketplaces and off for third-party/local ones; `DISABLE_AUTOUPDATER` disables it, `FORCE_AUTOUPDATE_PLUGINS=1` re-enables plugin updates alone; `autoUpdate: true` per `extraKnownMarketplaces` entry in managed settings ([discover-plugins, "Configure auto-updates"](https://code.claude.com/docs/en/discover-plugins#configure-auto-updates)). Background pulls of private marketplaces disable git credential helpers over HTTPS; SSH keys in `ssh-agent` work; `gh auth setup-git` is the documented fix for the re-clone fallback ([plugin-marketplaces, "Private repositories"](https://code.claude.com/docs/en/plugin-marketplaces#private-repositories)).
- Containers/CI: `CLAUDE_CODE_PLUGIN_SEED_DIR` (read-only, mirrors `~/.claude/plugins`, no auto-update, "works in both interactive mode and non-interactive mode with the `-p` flag") and `CLAUDE_CODE_PLUGIN_CACHE_DIR` at build time ([plugin-marketplaces, "Pre-populate plugins for containers"](https://code.claude.com/docs/en/plugin-marketplaces#pre-populate-plugins-for-containers)).
- `--plugin-dir` has no versioning: it is whatever is on disk at Fire time, which for a Daemon that owns its own checkout of the harness is the simplest pin (git tag/commit of that checkout). `claude plugin tag` creates `{name}--v{version}` release tags (local CLI help, 2.1.267).

### 7. `--print` limitations that matter

- Skills/commands work: "include `/skill-name` in the prompt string and Claude Code expands it before running" ([headless](https://code.claude.com/docs/en/headless)); for a plugin skill that is `/afk:afk-pickup`.
- Without `--bare`, `-p` loads everything an interactive session would (hooks, `.mcp.json`, plugins, `~/.claude`), shows no trust dialog and no per-server approval prompt ([headless, bare mode](https://code.claude.com/docs/en/headless#start-faster-with-bare-mode)). `--bare` (2.1.81+) skips hooks, skills, subagents, plugins, MCP, auto memory and `CLAUDE.md` and disables OAuth (needs `ANTHROPIC_API_KEY`), so it is **not** usable for a subscription-paced Daemon, and it is slated to become the `-p` default "in a future release" ([headless](https://code.claude.com/docs/en/headless#start-faster-with-bare-mode)). If that lands, `--plugin-dir` remains the documented way to hand a plugin to a bare session ("A plugin: `--plugin-dir <path>`, `--plugin-url <url>`").
- Things that never load in `-p` from an untrusted folder: project `permissions.allow`/`additionalDirectories`, frontmatter hooks in project subagents, project `@skills-dir` plugins, `extraKnownMarketplaces` from the repo or `--add-dir` ([permissions](https://code.claude.com/docs/en/permissions#what-runs-before-you-trust-a-folder)). Trust can be granted by hand: `projects["<path>"].hasTrustDialogAccepted: true` in `~/.claude.json`.
- No teammates (§5). Background monitors run only in interactive sessions ([plugins-reference, Monitors](https://code.claude.com/docs/en/plugins-reference#monitors)). MCP OAuth flows cannot complete in `-p` ([mcp](https://code.claude.com/docs/en/mcp)).
- `--output-format stream-json` `system/init` reports `plugins` and `plugin_errors` (including `--plugin-dir` load failures) so a Fire can fail fast when the plugin did not load ([headless, "Fail CI when a plugin or MCP server doesn't load"](https://code.claude.com/docs/en/headless#fail-ci-when-a-plugin-or-mcp-server-doesnt-load)).
- `--permission-prompts none` removes `AskUserQuestion` and auto-denies anything unresolved ([headless](https://code.claude.com/docs/en/headless)); `--setting-sources user` excludes project settings and `.mcp.json` altogether ([mcp](https://code.claude.com/docs/en/mcp#project-scope)).
- Setup hooks: `-p --init` / `--maintenance` and `--init-only` run `Setup` hooks, a documented slot for one-time dependency installation from a plugin ([hooks, Setup](https://code.claude.com/docs/en/hooks#setup)).

### 8. User-level `~/.claude/skills` and `~/.agents/skills`

- `~/.claude/skills/<name>/SKILL.md` is the documented personal location ("All your projects on this machine"); a `<skill-name>` entry there may be a symlink to a directory elsewhere and is loaded once even if several locations point at the same target ([skills, "Choose where skills load"](https://code.claude.com/docs/en/skills#choose-where-skills-load)).
- `~/.agents/skills` is **not documented** anywhere in the Claude Code docs (no hit in the skills, plugins or settings pages). On this Host it works only because `~/.claude/skills/<name>` are symlinks into `~/.agents/skills/<name>` (checked locally: `ls -la ~/.claude/skills`). `afk-resolve` reading `~/.agents/skills/research/SKILL.md` by path is therefore a Host convention, not a Claude Code contract; a plugin that vendors or depends on the `research` skill removes that dependency. Plugin `dependencies` (semver, auto-installed from marketplaces) exist for exactly this ([plugins-reference, manifest](https://code.claude.com/docs/en/plugins-reference#plugin-manifest-schema)).

## Implications for the distribution-shape decision (#2)

1. **A plugin is the right carrier for the model-facing half** (skills, agents, hooks, MCP, scripts via `${CLAUDE_PLUGIN_ROOT}`), loaded per Fire with `--plugin-dir <harness-checkout>/plugin` (no install state, versioned by the checkout) or installed once at user scope from a marketplace on the Host (`enabledPlugins` in `~/.claude/settings.json`, pinned by `version`/`sha`). Both paths are non-interactive-safe; nothing needs to be written into the Target Project checkout, which is what makes the harness "bring your own repo".
2. **The Host still owns a settings layer** because plugins cannot ship `env`/`permissions`: `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS`, allowlists, `skipDangerousModePermissionPrompt`, model defaults go in `~/.claude/settings.json` (or a per-Daemon `CLAUDE_CONFIG_DIR`) or a `--settings` JSON the `agent-run` wrapper passes. Under `bypassPermissions` the allowlists matter little, so this layer is small.
3. **Drop the Agent Teams assumption**: under `--print` the roster is subagents, `TeammateIdle` is dead code, and `TaskCompleted` is the only team hook that fires. The Spec should describe implementer/reviewer/verifier as subagents (`agents/` in the plugin) and not require `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS`.
4. **Per-Target-Project config cannot live in the plugin's `settings.json`**; use plugin `userConfig` (headless: `--settings '{"pluginConfigs":...}'`, exported as `CLAUDE_PLUGIN_OPTION_*`) or, simpler and already the harness's style, an env file the Daemon sources and passes to hooks/MCP via `env`. The Harness config in `CONTEXT.md` maps onto either.
5. **Plan for `--bare` becoming the `-p` default**: keep the wrapper explicit (`--plugin-dir`, `--settings`, `--add-dir`, `--mcp-config`) so a Fire keeps working if auto-discovery is turned off; today `--bare` is off the table because it disables OAuth.
6. Bundle or declare a dependency on the `research` skill instead of reading `~/.agents/skills`, and name plugin skills with the namespace in mind (`/afk:pickup` rather than `/afk:afk-pickup`).
