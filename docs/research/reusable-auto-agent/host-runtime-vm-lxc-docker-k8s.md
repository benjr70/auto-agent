## Short answer

**A full VM is the only runtime where every current Host need is met by documented, supported behaviour. Proxmox LXC is a close second but requires `nesting=1` + `keyctl=1` for Docker and gives the Daemon a shared host kernel. A Docker container works for the Daemon and headed Chrome only if it is `--privileged` (Docker-in-Docker) or handed the host's Docker socket (root-equivalent on the host), and needs an Xvfb display; the Electron SUID sandbox must be disabled. A Kubernetes pod inherits every Docker-container constraint plus `privileged: true` (rejected by the Baseline Pod Security Standard) and adds a control plane that buys nothing for a single-replica, one-Fire-at-a-time daemon.**

What the Host actually needs, derived from the live scripts (section 1), and what each runtime documents (sections 2-5), followed by the comparison table (section 6) and implications for #10 (section 7).

## 2. Proxmox VM (QEMU/KVM, cloud-init)

- **Isolation**: a VM has its own kernel. Proxmox's own guidance for application containers reads: "for use cases demanding maximum isolation and the ability to live-migrate, nesting containers inside a Proxmox QEMU VM remains a recommended practice" ([Linux_Container](https://pve.proxmox.com/wiki/Linux_Container)). Claude Code's sandbox comparison says the same: "A dedicated virtual machine provides the strongest separation, with its own kernel ... Use this approach when you are evaluating untrusted code, when your security policy requires kernel-level separation between the agent and the host" ([sandbox-environments](https://code.claude.com/docs/en/sandbox-environments)). Setup effort is rated "High" in that table.
- **Nested Docker**: Docker inside a VM is ordinary Docker on a Linux kernel; no Proxmox feature flag is involved. Proxmox "nested virtualization" is only needed "when you run a hypervisor, like PVE or others, inside a virtual machine" ([Nested_Virtualization](https://pve.proxmox.com/wiki/Nested_Virtualization)) — Docker is not a hypervisor, so the VM needs no nested-virt exposure. The live Host confirms: `systemd-detect-virt=kvm`, Docker with cgroup v2 + overlayfs works with no special VM options.
- **Headed Chrome / Electron**: a full desktop session is possible (the live Host runs GNOME/XWayland on `:0`), or Xvfb. Both Playwright ("On Linux agents, headed execution requires Xvfb to be installed" — [ci](https://playwright.dev/docs/ci)) and the SUID sandbox (`chrome-sandbox` root-owned, mode 4755 — [suid_sandbox_development](https://chromium.googlesource.com/chromium/src/+/main/docs/linux/suid_sandbox_development.md)) are satisfiable because root exists inside the VM.
- **systemd**: native.
- **Credentials**: `~/.claude/.credentials.json` mode `0600` on a persistent root disk ([authentication](https://code.claude.com/docs/en/authentication)); nothing to mount.
- **Provisioning**: Proxmox cloud-init supports ready-made cloud images (`.qcow2`), sets user, password, SSH keys, network, and takes custom user-data via `cicustom` snippets; workflow is `qm importdisk` → `qm set <id> --ide2 <storage>:cloudinit` → `qm template <id>` → clone ([Cloud-Init_Support](https://pve.proxmox.com/wiki/Cloud-Init_Support)). Limits stated there: every cloud-init VM needs a CD-ROM drive, snippets must live on storage that supports them. Ubuntu *Desktop* is not a cloud image; a cloud-init Host would be Ubuntu Server + Xvfb (or an installed desktop session via user-data), which is a change from today's hand-built GNOME box.
- **Resources**: memory is either fixed or ballooned between `minimum memory` and `memory` ([qm](https://pve.proxmox.com/pve-docs/qm.1.html)). The Daemon's 6.4 GB RSS peak + per-PR compose stacks + Chrome/Electron means the current 12 GB allocation is the realistic floor.

## 3. Proxmox LXC

- **Privileged vs unprivileged**: unprivileged is the default (`--unprivileged` "For creation, the default is 1" — [pct.conf](https://pve.proxmox.com/pve-docs/pct.conf.5.html)); "The root UID 0 inside the container is mapped to an unprivileged user outside the container ... The LXC team thinks unprivileged containers are safe by design." Privileged containers: "The LXC team considers this kind of container as unsafe, and they will not consider new container escape exploits to be security issues ... privileged containers should only be used in trusted environments" ([Linux_Container](https://pve.proxmox.com/wiki/Linux_Container)).
- **Nested Docker**: two feature flags. `keyctl`: "For unprivileged containers only: Allow the use of the keyctl() system call. This is required to use docker inside a container." `nesting`: "Allow nesting. Best used with unprivileged containers with additional id mapping. Note that this will expose procfs and sysfs contents of the host to the guest." ([pct.conf](https://pve.proxmox.com/pve-docs/pct.conf.5.html)). The `pct` man page adds that `nesting` "Expose procfs and sysfs to allow nested containers. Note that systemd also uses this to isolate services" ([pct](https://pve.proxmox.com/pve-docs/pct.1.html)). So an unprivileged LXC with `features: nesting=1,keyctl=1` is the documented configuration for Docker; the docs do **not** state which storage driver Docker will get on the LXC rootfs (overlay2 on ZFS-backed LXC is **not documented** either way). Proxmox's own preference is stated above: for "maximum isolation ... nesting containers inside a Proxmox QEMU VM remains a recommended practice."
- **Headed Chrome / Electron**: **not documented** by Proxmox. What the primary sources give: a display server inside the container is a userland matter (Xvfb, per Playwright [ci](https://playwright.dev/docs/ci)); the SUID sandbox needs a root-owned 4755 helper, which works inside an unprivileged LXC because in-container root is real to the container's processes; the Chromium user-namespace layer 1 needs unprivileged user namespaces ([sandbox/linux/README](https://chromium.googlesource.com/chromium/src/+/main/sandbox/linux/README.md)), whose availability inside an unprivileged LXC is not documented by Proxmox. A GPU/GNOME session inside LXC is not documented; treat headed = Xvfb.
- **systemd**: supported; "If the container uses systemd as an init system, please be aware the systemd version running inside the container should be equal to or greater than 220" and cgroup v2 needs systemd ≥ 231 ([Linux_Container](https://pve.proxmox.com/wiki/Linux_Container)). `nesting=1` is also what lets systemd's own service isolation work (`pct` quote above).
- **Credentials**: same as VM (persistent rootfs, `0600` file).
- **Claude Code specifics**: the bash sandbox's bubblewrap "can't mount a fresh `/proc` filesystem" in an unprivileged container; `enableWeakerNestedSandbox: true` is the documented workaround ([sandboxing troubleshooting](https://code.claude.com/docs/en/sandboxing)). The Daemon does not use the bash sandbox today (bypassPermissions), so this is only relevant if #10 chooses to layer it.
- **Resources**: `memory` default 512 MB, `swap` 512 MB, `cores` "can use all available cores by default" ([pct.conf](https://pve.proxmox.com/pve-docs/pct.conf.5.html)); memory maps to the cgroup limit, and the container "can use additional swap memory from the host swap space" ([Linux_Container](https://pve.proxmox.com/wiki/Linux_Container)). No guest kernel, so the same 12 GB budget goes further than in a VM, but the FUSE warning ("usage of FUSE mounts inside a container is strongly advised against, as containers need to be frozen for suspend or snapshot mode backups") applies to snapshot backups of a container that has Docker inside.
- **Provisioning**: `pct create` from a template with `--features nesting=1,keyctl=1 --unprivileged 1`; no cloud-init (Proxmox cloud-init is a VM feature — [Cloud-Init_Support](https://pve.proxmox.com/wiki/Cloud-Init_Support)); an in-container script must do the rest.

## 4. Docker container

Three sub-options for the per-PR stacks, all documented by Docker as root-equivalent somewhere:

1. **Docker-in-Docker** (`docker:dind` sidecar or inside the image): "`--privileged` is required for Docker-in-Docker to function properly, but it should be used with care" ([hub.docker.com/_/docker](https://hub.docker.com/_/docker)). Persist `/var/lib/docker` with a volume, else every image build is lost on restart (same page). The rootless variant does not remove the flag: `docker run -d --name dind-rootless --privileged docker:25.0-dind-rootless` ([rootless tips](https://docs.docker.com/engine/security/rootless/)).
2. **Host socket mount** (`-v /var/run/docker.sock:/var/run/docker.sock`): "only trusted users should be allowed to control your Docker daemon" because bind mounts let a container "share your root filesystem (or even your root block device)" ([engine/security](https://docs.docker.com/engine/security/)); "The `docker` group grants root-level privileges to the user" ([linux-postinstall](https://docs.docker.com/engine/install/linux-postinstall/)). Note that the per-PR stacks then run as **siblings** of the Daemon container on the host daemon, so `docker compose down -v --rmi local` cleans up host-level resources and port blocks bind on the host, not inside the Daemon's namespace.
3. **Rootless Docker on the host** with the Daemon container talking to it: needs `newuidmap`/`newgidmap` and ≥ 65,536 sub-UIDs; systemd user service, survives logout only with `loginctl enable-linger`; cgroup limits (`--memory`, `--cpus`) "supported only when running with cgroup v2 and systemd"; ports < 1024 need `CAP_NET_BIND_SERVICE` on `rootlesskit` ([rootless](https://docs.docker.com/engine/security/rootless/), [tips](https://github.com/docker/docs/blob/main/content/manuals/engine/security/rootless/tips.md)). Docker's own post-install page points here: "For stronger isolation, use Rootless mode or run Docker in a virtual machine."

Other constraints:

- **Headed Chrome**: Playwright's image `mcr.microsoft.com/playwright:v1.63.0-noble` ships Xvfb; recommended run flags are `--init` ("to avoid special treatment for processes with PID=1 ... a common reason for zombie processes") and `--ipc=host` ("Without it, Chromium can run out of memory and crash"); "Using `--cap-add=SYS_ADMIN` when developing locally" is the documented escape hatch when Chromium fails to launch ([docker](https://playwright.dev/docs/docker)). Running as `root` "disables the Chromium sandbox"; the sandbox-on path is a non-root user plus the shipped `seccomp_profile.json` (same page). The Host's wrapper insists on **real Google Chrome** (`--browser chrome`), which is not in the Playwright image and would be an apt install in the Dockerfile.
- **Electron**: the SUID helper needs `root:root 4755` (`chrome_sandbox_usable` in `provision-box.sh`, matching Chromium's [suid_sandbox_development](https://chromium.googlesource.com/chromium/src/+/main/docs/linux/suid_sandbox_development.md) `chown root:root` / `chmod 4755`). Inside a container that is achievable at image build time, but the layer-1 user-namespace sandbox needs unprivileged user namespaces, and Docker's default seccomp profile denies `clone` for new namespaces ("Deny cloning new namespaces. Also gated by `CAP_SYS_ADMIN` for CLONE_* flags, except `CLONE_NEWUSER`") and `unshare` ([seccomp](https://docs.docker.com/engine/security/seccomp/)); this is what Playwright's `SYS_ADMIN` / custom `seccomp_profile.json` advice works around. The fallback the Host already implements, `ELECTRON_DISABLE_SANDBOX=1`, is honoured by Electron's main delegate (`if (env->HasVar(kElectronDisableSandbox)) command_line->AppendSwitch(kNoSandbox)` — [electron_main_delegate.cc](https://github.com/electron/electron/blob/main/shell/app/electron_main_delegate.cc)), and Electron's docs say of `--no-sandbox`: "We highly recommend that you only use this flag for testing purposes, and **never** in production" ([sandbox tutorial](https://www.electronjs.org/docs/latest/tutorial/sandbox)). Playwright's Electron driver is "experimental" ([class-electron](https://playwright.dev/docs/api/class-electron)); the Host attaches over CDP `:9222` instead, which Playwright's Electron page does not document.
- **systemd / supervision**: a container has no init unless you add one; Docker's own advice is `--init` (above). Daemon supervision would move to `restart: unless-stopped` plus a supervisor in-image, and the Dashboard's `journalctl`/`systemctl` probes (map #1 A.6) would need a different source.
- **`claude --print`**: Claude Code "refuses to start with this flag [`--dangerously-skip-permissions`] when running as root, so run the container, VM, or sandbox runtime as a non-root user" ([sandbox-environments](https://code.claude.com/docs/en/sandbox-environments)); "The CLI rejects this flag when launched as root, so confirm `remoteUser` is set to a non-root account" ([devcontainer](https://code.claude.com/docs/en/devcontainer)). A `-p` session "runs the hooks in a project's `.claude/settings.json` and connects the servers in its `.mcp.json`, even in a folder you've never trusted" ([headless](https://code.claude.com/docs/en/headless)) — this is the same in every runtime and is what spawns the orphaned MCP servers noted in map #1 §6.1; `--init` in a container would at least reap zombies.
- **OAuth credential persistence**: "Claude Code stores its authentication token, user settings, and session history under the `~/.claude` directory. It stores your OAuth account, personal MCP servers, and per-project trust in `~/.claude.json`, a separate file outside that directory, so mounting a volume at `~/.claude` alone doesn't keep you signed in. Mount a named volume at `~/.claude` and set `CLAUDE_CONFIG_DIR` to the same path so Claude Code writes `.claude.json` inside the volume" ([devcontainer](https://code.claude.com/docs/en/devcontainer)). On Linux the credential is `~/.claude/.credentials.json` mode `0600` and is refreshed by Claude Code itself; when refresh fails "each model request fails with `Login expired · Please run /login` until you sign in again" ([authentication](https://code.claude.com/docs/en/authentication)). The container alternative is `claude setup-token` → `CLAUDE_CODE_OAUTH_TOKEN`, "a one-year OAuth token" that "can only make model requests" and which `--bare` does not read (same page). Either way the docs warn: "When executed with `--dangerously-skip-permissions`, dev containers do not prevent a malicious project from exfiltrating anything accessible inside the container, including the Claude Code credentials stored in `~/.claude`" ([devcontainer](https://code.claude.com/docs/en/devcontainer)).
- **Persistent volumes** for the checkout and logs: plain named volumes / bind mounts; nothing runtime-specific. The Daemon's log dir, `~/.claude/projects/*` transcripts (which the Dashboard scrapes) and the per-PR docker image cache all need volumes.
- **Resources**: "By default, a container has no resource constraints" ([resource_constraints](https://docs.docker.com/engine/containers/resource_constraints/)); set `--memory` deliberately because a 6.4 GB RSS peak plus DinD image builds inside one cgroup will otherwise contend with the host.

## 5. Kubernetes pod

Everything in section 4 applies (a pod is one or more OCI containers), plus:

- **DinD requires `privileged: true`**: "Processes in privileged containers are essentially equivalent to root on the host" ([pod-v1 API](https://kubernetes.io/docs/reference/kubernetes-api/workload-resources/pod-v1/)). The **Baseline** Pod Security Standard forbids it ("Privileged containers are essentially unrestricted and must be disallowed" — allowed values `undefined/nil`, `false`), forbids host namespaces, and forbids `hostPath` volumes; **Restricted** additionally requires non-root and dropping capabilities ([pod-security-standards](https://kubernetes.io/docs/concepts/security/pod-security-standards/)). A socket-mount variant needs a `hostPath` to the node's runtime socket, which is Baseline-forbidden and is "a volume type [that] presents many security risks" ([volumes](https://kubernetes.io/docs/concepts/storage/volumes/)); modern clusters run containerd, so there is often no Docker socket on the node at all (**not documented** for the Daemon's Compose use).
- **State**: a one-replica StatefulSet with `volumeClaimTemplates` gives "stable, persistent storage" and "stable, unique network identifiers"; storage "must either be provisioned by a PersistentVolume Provisioner ... or pre-provisioned by an admin", and "Deleting and/or scaling a StatefulSet down will not delete the volumes" ([statefulset](https://kubernetes.io/docs/concepts/workloads/controllers/statefulset/)).
- **Benefit for a one-Fire-at-a-time Daemon**: the things Kubernetes adds (scheduling across nodes, replicas, rolling updates, service discovery) are unused by a single-replica process holding a repo-wide `AFK:in-progress` lock. What it costs: a cluster to run (control plane + node) on the same Proxmox box, a privileged PSS namespace, PV provisioning, and a display (Xvfb in-pod). Not documented anywhere in the sources above: running headed Chrome/Electron in a pod; Kubernetes docs are silent on X displays.

What breaks in `--print` mode is runtime-independent: `-p` still loads `.mcp.json` servers and hooks without a trust prompt ([headless](https://code.claude.com/docs/en/headless)); `--bare` would skip them but also "never reads OAuth credentials" (same page), so the subscription-paced Daemon cannot use it; `bypassPermissions` is refused as root in every runtime ([sandboxing](https://code.claude.com/docs/en/sandboxing)).

## 7. Implications for the Host runtime decision (#10)

1. **The Verification Harness dictates the runtime, not the Daemon.** The Daemon itself (bash + `claude -p` + `gh` + Node) runs anywhere non-root with a persistent `~/.claude`. What forces a VM-or-LXC choice is Smart-Smoker's bring-your-own Verification Harness: headed real Chrome, Electron with CDP, and per-PR Compose stacks. #10 should decide the Host runtime for the **generic** Daemon and let the Target Project's Harness config declare extra Host needs (display, Docker), rather than baking a GUI box into the harness.
2. **Proxmox VM stays the reference Host; make it cloud-init reproducible.** It is the only option where every need is met by documented behaviour and where Proxmox itself says application containers belong. The one change worth making is Ubuntu Server cloud image + Xvfb (Playwright's own headed recipe) instead of a hand-installed Ubuntu Desktop with a logged-in GNOME session, which would retire `.mutter-Xwaylandauth.*` globbing in `resolve-display-env.sh` in favour of a fixed `DISPLAY`. Whether the screenshot tour is visually equivalent under Xvfb versus XWayland is **not documented** and needs the #9 prototype.
3. **Proxmox LXC is the cheap second Host for a project without a GUI harness.** `--unprivileged 1 --features nesting=1,keyctl=1` is the documented Docker recipe; the cost is `nesting` exposing host procfs/sysfs and a shared kernel under `bypassPermissions`. Reasonable for a second Target Project on the same Proxmox node once the harness is generic; not the reference.
4. **A Docker image of the Daemon is worth having, but not as the Host for this Target Project.** It needs `--privileged` DinD or the host socket, Xvfb, real Chrome baked in, `ELECTRON_DISABLE_SANDBOX=1`, `--init --ipc=host`, and the `~/.claude` volume + `CLAUDE_CONFIG_DIR` dance. It is the right shape for Target Projects whose Verification Harness is headless and Docker-free (or for CI-style use with `CLAUDE_CODE_OAUTH_TOKEN`), so the extraction should keep the Daemon container-friendly (no `journalctl` dependency in the Dashboard, `--init`-safe process tree, config dir env-driven) without making it the default.
5. **Kubernetes: no.** For a single-replica process holding a repo-wide lock it adds a control plane, a Privileged-PSS namespace for DinD, PVC provisioning, and no documented path for a display, while providing scheduling/replica features the Daemon cannot use.
6. **Concrete numbers for #10 / #9**: size a VM Host at ≥ 12 GB RAM and ≥ 80 GB disk (Daemon peak 6.4 GB RSS + swap, plus per-PR images; the current 50 GB disk is at 93%), cap the Daemon's own cgroup with a systemd `MemoryMax`, and add a reaper for per-Fire MCP servers regardless of runtime since `-p` spawns them and nothing reaps them.
